IMPORTANT, as requested: SITE_URL must still be set in Vercel. This constant is only the

whatever SITE_URL says, while a missed-SITE_URL robots.txt/sitemap.xml will fall back to
this hardcoded value. Keep them in sync.

2. ACCOUNT PROFILE PAGE — NULL CHECK INSTEAD OF NON-NULL ASSERTION
============================================================
Commit: a28a880

src/app/(storefront)/account/(protected)/page.tsx used session!.customerId, trusting
that the (protected) layout had already redirected if there's no session. Next.js
evaluates a layout and its page concurrently, so on an unauthenticated request this page
component still ran and threw "Cannot read properties of null (reading 'customerId')" —
harmless to the actual response (the layout's redirect() still won), but logged as an
error on every unauthenticated hit.

Replaced with an explicit check: if (!session) redirect("/account/login"); directly in
the page, before touching session.customerId. Verified live against a real `next start`
build — the log is now completely clean on an unauthenticated request to this page
(previously showed the TypeError on every hit).

4. LOWEST REVALIDATE PER STOREFRONT ROUTE
============================================================
Report only — no code change. Figures below are from a fresh `npm run build` on this
branch (same build used to verify item 3).

Every static/SSG public storefront page builds with the same figure: 5m (300 seconds).
This is the cascade documented in PERF-REPORT-2.txt's Task 2: (storefront)/layout.tsx
calls getActiveCampaigns() at revalidate: 300 for the header's sale-dot indicator, and
Next.js takes the lowest revalidate across every layout and page of a route — so every
page under that layout inherits this 300s ceiling regardless of its own setting.

  Route                           Revalidate   Expire
  /                                5m            1y
  /men                             5m            1y
  /men/[category] (10 pages)       5m            1y     — each individually
  /women                           5m            1y
  /women/[category] (10 pages)     5m            1y     — each individually
  /new                             5m            1y
  /sale                            5m            1y
  /size-guide                      5m            1y
  /cart                            5m            1y
  /product/[slug] (34 pages)       5m            1y     — each individually
  /journal                         5m            1y
  /journal/[slug] (3 pages)        5m            1y     — each individually
  /lookbook                        5m            1y
  /contact                         5m            1y
  /faq                             5m            1y
  /privacy                         5m            1y
  /shipping-returns                5m            1y
  /terms                           5m            1y
  /account/login                   5m            1y
  /account/register                5m            1y

One exception, NOT subject to the layout cascade because it's a root-level metadata-route
file outside the (storefront) route group entirely:

  /sitemap.xml                     1h            1y   (its own explicit
                                                        `export const revalidate = 3600`
                                                        in src/app/sitemap.ts)

/robots.txt has no revalidate column in the build output at all — it has no
`export const revalidate` of its own and isn't under (storefront), so Next treats it as
plain static output with no ISR timer (equivalent to being revalidated only on a new
deploy/build).

Every other public route (/account/*, /admin/*, /api/*, /checkout, /search,
/order-status, /order/[number], /track) is fully dynamic (ƒ) — rendered per-request, so
it has no revalidate value to report at all.

For judging whether 300s is too aggressive: the pages this actually matters for (sale-
badge/price accuracy) are the product/category/home pages — those need a bound of some
kind because of the campaign-boundary issue from PERF-REPORT-2.txt's Task 2. The pages
that inherit 300s purely as a side effect of the layout cascade and have nothing
time-sensitive of their own are: /journal, /journal/[slug], /lookbook, /contact, /faq,
/privacy, /shipping-returns, /terms, /account/login, /account/register. If 300s feels too
aggressive for the regeneration cost of those specific pages (legal/content pages that
rarely change), the two options are: (a) accept the current trade-off as documented
(small over-regeneration cost on a handful of low-traffic, cheap-to-render pages, in
exchange for the header's sale indicator never drifting more than 5 minutes anywhere on
the site), or (b) pull the header's saleActive flag out of the shared layout and into a
narrower mechanism that doesn't impose a route-wide ceiling (e.g. a small client
component that fetches it separately, at the cost of one extra request per page view
instead of a cache-layer dependency) — that's a real architectural change, not a one-line
tweak, so I didn't make it without being asked.
