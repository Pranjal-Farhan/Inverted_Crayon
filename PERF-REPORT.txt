1. ROOT CAUSES FOUND, RANKED BY LIKELY INVOCATION IMPACT
================================================================================

1a. src/app/(storefront)/layout.tsx called getCustomerSession() (which calls
    cookies() in src/lib/session.ts) on every request, solely to pass a
    customerName string down to Header.tsx for two small UI decisions (the
    account link's href, and a label swap). Next.js treats any cookies() call
    inside a shared layout as "this entire route tree is dynamic" — there is
    no partial opt-out in the caching model this app uses (cacheComponents is
    off). This single call was the reason the baseline build showed every
    public route as dynamic (ƒ) except /_not-found and /admin/login — the
    single highest-impact finding in this audit.

1b. The same layout performed 4 uncached database reads on every request,
    independent of (1a): db.campaign.findFirst (sale-badge flag),
    db.contentBlock.findUnique (home_hero, for brand name/logo),
    getChatWidgetSettings() (db.storeSetting.findUnique), and
    db.category.findMany (header nav). None were tagged or cached.

1c. src/proxy.ts ran on the Node.js runtime (Next 16 changed this from Edge)
    on every single request matched by its catch-all matcher — including bot
    probes and crawler hits — purely to set 5 static security headers. No
    auth, no redirects, no other logic.

1d. Every individual storefront page additionally ran its own uncached,
    per-request queries on top of (1b): home page (5 queries), product page
    (3 queries + a session read + a wishlist lookup), men/women category
    pages (a category lookup + a full-catalog scan), cart page (2 queries),
    men/women hub pages (4 queries each). None were cached or tagged.

1e. src/lib/plp.ts's getPLPResults() loaded the entire matching product
    catalog on every call (no SQL-level filter for size/color/price/tag/
    stock) and filtered, sorted, and paginated in JavaScript — used by
    /men/[category], /women/[category], /new, /sale, and /search. These
    pages also read searchParams directly for that filtering, which
    independently forces dynamic rendering regardless of (1a)/(1b).

1f. No robots.ts, sitemap.ts, or vercel.json existed anywhere in the repo.
    Crawlers had zero guidance and could (and very likely did) hit every
    dynamic route repeatedly, including /admin, /account, /cart, /checkout,
    and API routes that require auth anyway.

1g. Minor, pre-existing inefficiencies in client widgets: the search-
    suggestions hook debounced at 200ms with no AbortController and no
    client-side result cache; the abandoned-checkout capture re-sent on
    every blur of the email field even if nothing had changed.

FIX 8 — Database connection safety (REPORT ONLY, no code changed)
  - src/lib/db.ts already uses the correct globalThis singleton pattern for
    both the PrismaClient and the PrismaPg adapter — not a bug.
  - Risk, not a bug: the PrismaPg adapter is constructed with only a
    connectionString, no explicit pool size/idle-timeout. In a serverless
    deployment, every concurrent function instance opens its own pool

    concurrent load this can approach a Postgres provider's connection
    limit. This is a known Vercel+Postgres pattern, not specific to this
    codebase, and the right fix depends entirely on which Postgres provider
    is used in production (most offer a pooled/PgBouncer connection string
    as a drop-in DATABASE_URL replacement) — see section 6.

PUBLIC ROUTES STILL DYNAMIC (ƒ), AND WHY — all deliberate:
  /men/[category], /women/[category], /new, /sale
      Read searchParams to drive server-side sort/filter/pagination,
      preserving the existing shareable-URL behavior. The safer,
      lower-risk call per the task's own fallback guidance, rather than
      rewriting filtering to run client-side. The expensive unfiltered
      catalog fetch underneath is cached (src/lib/plp.ts), so this no
      longer costs a DB round-trip on every request even though the
      function itself still runs.
  /search
      Inherently query-string-driven; same catalog-cache mitigation.
  /size-guide
      Reads a ?product= searchParam to pick which chart to show; low-
      traffic informational page. The per-slug DB read is cached.
  /order-status, /order/[number], /track
      Order-number lookup pages — deliberately never cached, by design
      from the earlier order-tracking feature: caching a specific order's
      page risks serving one visitor's order data to the next on a cache
      hit. This is a correctness/privacy choice, not an oversight.
  /account, /account/addresses, /account/orders, /account/orders/[number],
  /account/returns, /account/wishlist, /account/back-in-stock, /checkout
      Personalized, session-gated pages — correctly stay dynamic.
  /admin/* (all)
      Admin pages, by design, always read fresh data.
  /api/* (all)
      API and payment-callback routes.

5. DELIBERATELY NOT CHANGED, AND WHY
================================================================================

  - checkout.ts and every price/stock-guard code path: never touched to read
    through a cache. It imports getShippingRates (the fresh version from
    store-settings.ts), not the cached getCachedChatWidgetSettings/
    getCachedStoreInfo from public-cache.ts. Confirmed by grep: zero files
    under src/actions/ or src/app/admin/ import public-cache.ts at all.
  - cacheComponents was NOT enabled. The task's own ground rules say not to
    enable it without completing the migration safely, and this codebase has
    zero existing Suspense-boundary structure around dynamic data — turning
    it on would be a much larger, separately-scoped migration. Flagged as a
    recommendation in section 6, not attempted here.
  - Category/search/new/sale/size-guide listing pages were NOT rewritten to
    filter client-side, even though that would let them go fully static too.
    Moving server-side filter/sort/pagination logic to the client is a
    materially larger, riskier change (shareable-URL semantics, SEO,
    pagination) than this task's risk budget — the ground rules explicitly
    sanction falling back to "keep it, but cache the base query" in this
    case, which is what was done.
  - Order-status/order/track pages were NOT cached, by design — see section
    3. Caching a specific order lookup risks a privacy leak across visitors.
  - revalidateTag's "max" (stale-while-revalidate) profile was NOT used, in
    favor of { expire: 0 } (immediate) — see Fix 3 above. Trades a little of
    "max"'s perf benefit for the correctness guarantee that stock/price
    badges are right on the very next visit after an admin change.
  - Fix 7/8 (images, DB connection pooling): report only, no code changed,
    per the task's own instruction not to guess at infra changes blindly.
  - A handful of lower-traffic internal links (pagination/filter links
    within the already-dynamic PLP pages, pointing at other variations of
    that same still-dynamic route) were not swept for prefetch={false} —
    diminishing returns, since the user is already paying that page's
    dynamic cost on every such click regardless of prefetch.


6. RISKS AND OWNER DECISIONS NEEDED
================================================================================

  - cacheComponents (Next 16's newer caching model): NOT enabled. Could
    shrink the public-cache.ts boilerplate and give finer-grained partial
    prerendering, but migrating safely means restructuring every dynamic
    read behind Suspense boundaries — a real, separately-scoped project.
    Recommend evaluating it only after confirming this branch's impact on
    actual invocation counts.
  - DB connection pool sizing (Fix 8): no code changed. If the production
    DATABASE_URL points at a direct (non-pooled) Postgres connection rather
    than a pooler/PgBouncer endpoint, concurrent serverless instances could
    approach the database's max_connections under real traffic. This is a
    deployment-configuration decision (which connection string to use), not
    a code bug — needs the owner to check which Postgres provider/plan is
    in use and whether it offers a pooled endpoint.
  - Images (Fix 7): no code changed. If ImgBB-hosted product photos are
    uploaded at very large original sizes, pre-sizing at upload time is a
    bandwidth optimization worth considering later — not implemented here,
    as it's a feature change beyond "reduce invocations."
  - The { expire: 0 } (immediate) invalidation profile chosen throughout
    Fix 3 is more conservative (and slightly more DB load on the first
    request after any admin edit) than Next's generally-recommended "max"
    profile. This was a deliberate correctness-over-performance call because
    of the stock/price-badge concern — worth knowing it's there if Vercel's
    post-deploy numbers want to be squeezed further later.
  - This branch has NOT been pushed, merged, or deployed, per the task's own
    instructions. Someone needs to explicitly decide to merge and deploy it.


7. ESTIMATED REDUCTION (LABELED AS AN ESTIMATE) + WHAT TO MONITOR
================================================================================

This is an estimate, not a measurement — there is no access to this
deployment's actual Vercel invocation-by-route breakdown from this
environment. The baseline finding was that literally 100% of storefront page
views (plus every matched request's separate proxy invocation) counted as a
Vercel Function Invocation. After this branch:

  - The highest-traffic public pages (home, every product page, every
    category hub landing page, cart, contact, lookbook, journal) now serve
    from a static shell or build-time-prerendered page with zero function
    execution on a cache hit — only re-running at most once per hour per
    path, or on-demand right after an admin edit invalidates its tag.
  - proxy.ts, which ran on every single request including bot probes, no
    longer exists as a separate invocation at all.
  - For a typical storefront traffic mix (product/category/home pages
    usually dominate total page views over checkout/account/admin by a wide
    margin), this plausibly puts the reduction in the 60-85% range for
    Function Invocations specifically — but this is a judgment call based on
    the shape of the fix, not a number pulled from real traffic data.

WHAT TO MONITOR AFTER DEPLOYING:
  - Vercel's Usage/Observability tab, Functions breakdown, 24-48h after
    deploy, compared to the same window before — the only real measurement.
  - That admin edits still show up on the public site promptly (the Fix 3
    live test confirmed this works; worth re-confirming once on production
    data).
  - That checkout pricing/stock-guard behavior is unchanged (it reads
    straight from the database exactly as before — nothing about its logic
    was touched, only the caching added everywhere else).
  - Error rates / 404s on /product/[slug] and /journal/[slug] for items
    that didn't exist at build time — these fall back to on-demand ISR
    (dynamicParams stays true), so they should resolve normally, but it's
    worth a spot check.
