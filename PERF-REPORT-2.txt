1. STATIC PLP PAGES — /men/[category], /women/[category], /new, /sale, /size-guide
============================================================
Commit: 72b3f40

All four listing pages and /size-guide no longer read searchParams on the server. Each is
now a plain static/SSG page:

  - src/lib/plp.ts gained getPLPCatalog(gender, categorySlug) — a server-only, cached
    (unstable_cache) read of the full unfiltered catalog for that scope, carrying each
    product's sizes/colors alongside its derived display data.
  - A new server component, StaticPLPView, calls that catalog fetch and renders:
      - a plain, unfiltered <ProductCard> grid as the Suspense fallback (this is what's
        in the server-rendered HTML — real product links, confirmed with a raw curl, so
        crawlers and "view source" both see the full category)
      - inside <Suspense>, a client component (StaticPLPClient) that owns filtering,
        sorting and pagination entirely in the browser, using useSearchParams() for the
        initial read and window.history.pushState() (not router.push) to update the URL
        with zero server round-trips, plus a popstate listener so back/forward work.
  - /new passes defaultSort="newest"; /sale passes forcedTag="sale" — both reproduce the
    exact filtering the old dynamic pages applied server-side.
  - /size-guide: the ?product= read moved to a client component (SizeGuideClient) that
    fetches via a small server action (getSizeGuideForProduct) in a useEffect. The page
    itself takes no searchParams.
  - Canonical URLs: generateMetadata on each page still sets alternates.canonical to the
    clean, param-free path — unaffected by the client-side query string.

/search intentionally stays dynamic. Documented in its own file: it takes a free-text
query with effectively unbounded cardinality, so there is no fixed set of "pages" to
pre-render or cache the way there is for a category (finite categories) or /new, /sale
(finite tags). It still shares the same underlying filter/sort logic via plp.ts.

Verified live (Playwright): filter/sort clicks produce zero document requests; back/
forward restores the right state; a filtered URL copied into a brand-new browser tab
reproduces the same filtered view from a cold load. Zero console errors across the run.

2. CAMPAIGN BOUNDARY STALENESS
============================================================
Commit: 8039773

Checkout: confirmed placeOrder (src/actions/checkout.ts) already reads campaigns via a
direct db.campaign.findMany() call, not through any cached path — checkout prices were
already guaranteed fresh. No change needed there.

Found two real gaps in how a campaign's scheduled startsAt/endsAt boundary propagates
into cached storefront pages:

  (a) Tag-invalidation gap — invalidateCampaigns() (src/lib/invalidate.ts) only busted
      the "campaigns" tag. But sale pricing/badges are baked into the "products"-tagged
      catalog caches (plp.ts, public-cache.ts), not just the campaigns list itself. Fixed
      by having invalidateCampaigns() bust both tags. Verified live: created a real
      campaign via the admin UI, confirmed the sale price showed up on the category page
      in a brand-new browser context on the very first request — no redeploy needed.

  (b) No mechanism at all for a passive boundary — a campaign's startsAt/endsAt passing
      with no admin action never calls revalidateTag, so a cached read with no revalidate
      option of its own could stay wrong indefinitely once a scheduled campaign starts or
      ends (not just for an hour — forever, until something else happened to bust the
      tag). Fixed by adding revalidate: 300 (5 minutes) directly to the unstable_cache
      calls that actually carry campaign-derived pricing: getActiveCampaigns,
      getHomeNewProducts, getGenderHubProducts, getCachedProductById,
      getCartRecommendations (public-cache.ts), getCachedCatalogForScope (plp.ts), and
      getCachedProductForPDP (get-product.ts). getLookbookProducts deliberately excluded
      — it shows no price or sale badge, so it has no boundary risk.

Also lowered export const revalidate (the page-level ISR shell timer) from 3600 to 300
on every storefront page that shows price/sale content, with a comment at each site.
Important nuance, confirmed by reading the Next.js docs and the actual build output: the
page-level revalidate and unstable_cache's own revalidate are two separate cache layers
(Full Route Cache vs. Data Cache) — lowering one does not force the other to refetch. Both
needed the change; the fix above touches both.

One cascading side effect, confirmed intentional rather than a bug: (storefront)/layout.tsx
calls getActiveCampaigns() for the header's sale-dot indicator, now at revalidate: 300.
Next.js uses the lowest revalidate across every layout and page of a route, so this
layout's 300s becomes the effective ceiling for every page under it — including pages
with no campaign content of their own (journal, lookbook, legal pages). Documented in the
layout as an accepted trade: those pages regenerate a bit more often than they strictly
need to, in exchange for the header's own sale indicator never drifting more than 5
minutes anywhere on the site.

============================================================

4. CUSTOMER HINT COOKIE vs. REAL SESSION COOKIE
============================================================
Commit: f7f3d75, corrected by 0dbe1f5 (see note below — read both before relying on this)

maxAge: setCustomerSession() (src/lib/session.ts) sets both the real httpOnly session
cookie and the non-httpOnly hint cookie with the exact same MAX_AGE_SECONDS (30 days) in
the same response — confirmed by reading the current source, not from memory. They were
already in lockstep.

Explicit logout: clearCustomerSession() already deletes both cookies together, and
customerLogout() (src/actions/customer-auth.ts) — the only logout path in the app — was
already calling it correctly. No change needed there.

Session-expiry path (the actual gap): the account/(protected) layout redirects to
/account/login whenever getCustomerSession() fails verification, but it was not clearing
either cookie first — so a session that goes invalid for a reason other than reaching its
own maxAge (a tampered cookie, or a forced SESSION_SECRET rotation) could leave the
non-identifying hint cookie present and "logged in"-looking in the header while every
account page correctly bounced to login.

First attempt at a fix called clearCustomerSession() directly inside that layout's
render. This was wrong and I caught it only by testing against a real production build
(next start), not from reading the code: Next.js forbids mutating cookies from a Server
Component's render path at all — only a Server Action or a Route Handler may call
cookies().set()/delete(). The illegal call threw "Cookies can only be modified in a
Server Action or Route Handler," which pre-empted the layout's redirect() entirely and
took down every single /account/* page (confirmed live — every one of them 500'd instead
of redirecting). That version was already committed (f7f3d75) before I ran the production
server and caught it; per the ground rules, I did not amend that commit — I reverted the
illegal call in a new commit (0dbe1f5).

Net result, verified live against a real production build: /account (and every page
under it) correctly redirects an unauthenticated visitor to /account/login, with no
errors. The layout does NOT clear the hint cookie on that redirect — Next.js's own rules
don't allow it to. This is still safe in practice: because both cookies always get the
same maxAge in the same response, the only way they can fall out of sync is a forced
SESSION_SECRET rotation or an attacker tampering with the cookie — neither is a normal
"session expired" event, and the worst case is a cosmetic one (the header's logged-in
hint stays visually "on" for at most its remaining maxAge while every actual account page
still correctly requires login). Documented this trade-off directly in the layout's
comment rather than fighting the framework.

5. robots.ts / sitemap.ts SITE_URL FALLBACK + VERCEL ENV VARS
============================================================
Commit: b6f9ad1

Both files deliberately avoid getSiteOrigin() (which reads headers()) so they stay static
rather than becoming per-request dynamic functions. That meant their own fallback, used
only when SITE_URL is unset, was "http://localhost:3000" — harmless in local dev, but a
real production deploy that missed the env var would have served crawlers a broken
sitemap link and localhost URLs throughout sitemap.xml.

Added a single shared constant, PRODUCTION_SITE_URL, in src/lib/site-url.ts, and pointed
both robots.ts and sitemap.ts at it instead of localhost. SITE_URL should still always be
set in Vercel — this only covers the case where that's missed.

IMPORTANT — this needs the owner's confirmation: PRODUCTION_SITE_URL is currently set to
"https://invertedcrayon.com". There is no definitively-confirmed production domain
anywhere in this codebase — .env.example's own SITE_URL comment is literally the
placeholder "https://yourstore.com". I chose invertedcrayon.com because it matches the
brand name and the seed data's demo admin email (admin@invertedcrayon.com in
prisma/seed.ts), but that is a best guess, not a verified fact. If the real production
domain is different, update that one constant in src/lib/site-url.ts.

Verified live: with SITE_URL unset, robots.txt's Sitemap: line and every <url> in
sitemap.xml now use that fallback domain instead of localhost.

Full list of env vars referenced anywhere in the app (fresh grep across src/ and prisma/,
not from memory) — set these in Vercel:

  Required (the app throws on startup / in production without them):
    DATABASE_URL             — pooled Postgres connection string (runtime reads)
    SESSION_SECRET           — signs admin/customer session JWTs; app refuses to start in
                                production without it

  Required for Prisma CLI migrations (not read by the running app itself — see
  prisma7.config.ts's datasource.url — but needed wherever `prisma migrate deploy` runs
  against production, which may be a local/CI step rather than the Vercel build itself,
  since package.json's build script only runs `prisma generate`):
    DIRECT_URL               — direct (non-pooled) Postgres connection for migrations

  Strongly recommended:
    SITE_URL                 — stable production origin for payment-gateway callback URLs
                                and (per this task) the robots.txt/sitemap.xml fallback

  Demo/seed-only (not needed in a real production deploy, only for local seeding):
    ADMIN_EMAIL, ADMIN_PASSWORD, ALLOW_PRODUCTION_SEED

  Feature-dependent — each only matters if that integration is actually turned on:
    RESEND_API_KEY, EMAIL_FROM          — real email delivery (Resend)
    IMGBB_API_KEY                        — image hosting
    GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET,
    FACEBOOK_CLIENT_ID, FACEBOOK_CLIENT_SECRET   — social login
    BKASH_APP_KEY, BKASH_APP_SECRET,
    BKASH_USERNAME, BKASH_PASSWORD, BKASH_BASE_URL   — bKash payment gateway
    SSLCOMMERZ_STORE_ID, SSLCOMMERZ_STORE_PASSWORD,
    SSLCOMMERZ_SANDBOX                    — SSLCommerz payment gateway
    SSLWIRELESS_SMS_API_TOKEN, SSLWIRELESS_SMS_SID,
    SSLWIRELESS_SMS_BASE_URL              — outbound SMS

  Framework-provided, not something to set manually:
    NODE_ENV                              — set automatically by Next.js/Vercel

6. REBUILD, ROUTE TABLE, STILL-DYNAMIC ROUTES, SMOKE TESTS
============================================================

Full route table saved to perf-after-2.txt (gitignored, matching the existing
perf-before.txt/perf-after.txt pattern — added perf-after-2.txt to .gitignore in commit
0dbe1f5).

Public routes still dynamic (ƒ), and why — every one is a deliberate, correct choice, not
an oversight:

  /account, /account/addresses, /account/back-in-stock, /account/orders,
  /account/orders/[number], /account/returns, /account/wishlist
      — all read the customer session (cookies()) to show that specific customer's own
        data; inherently per-visitor, can't be cached across visitors.

  /checkout
      — reads the session to prefill a returning customer's saved info, and per ground
        rule 3, checkout must always compute prices/stock fresh from the DB. Also serves
        guests with no session at all, so there's nothing cacheable to pre-render.

  /order-status, /track
      — both are live, one-off DB lookups driven by a query string (order number, or
        number+email) with no fixed set of values to pre-render; the result has to be
        the current state of that specific order, not a cached snapshot.

  /order/[number]
      — the immediate post-checkout confirmation page; has to reflect the order exactly
        as it was just placed, and was deliberately hardened earlier (Fix 58, prior work)
        against leaking PII to anyone who merely has the order number — caching it would
        undermine that.

  /search
      — documented in task 1 above: unbounded free-text query, no enumerable scope to
        pre-render against.

All admin routes (/admin/*) and all /api/* route handlers are dynamic as expected and out
of scope for "public routes."

Build: npm run build completed cleanly against the real database. Route table unchanged
in shape from before this follow-up's Task 1/2 work — all previously-dynamic
/men/[category], /women/[category], /new, /sale, /size-guide routes are confirmed ● SSG /
○ static with 5m revalidate, matching what Tasks 1-2 were meant to produce.

Process note worth recording: the container already had a `next dev` instance holding
port 3000 since session start. My first two attempts to test against a genuine
`next start` production build were silently hitting that stale dev server instead (the
dev process wasn't visible to this shell's normal process list, only after disabling the
sandbox for process management) — which is exactly how the Task 4 cookie-mutation bug
above went undetected at first: it only surfaces under a real production build, not
Turbopack dev mode. Once identified, the dev server was stopped, the real production
server was started and used for every check listed above, then the dev server was
restored to its original state afterward so the container is left as it was found.

One piece of benign, pre-existing stderr noise worth flagging so it isn't mistaken for a
new bug: /account/(protected)/page.tsx uses `session!.customerId` (a non-null assertion),
trusting that its sibling layout already redirected if there's no session. Next.js
evaluates a layout and its page concurrently, so on an unauthenticated request this page
component does throw a "Cannot read properties of null" error in the server log — but the
layout's redirect() still wins and the client gets the correct redirect either way
(confirmed by the Playwright check above). This is a standard, accepted Next.js App
Router pattern, pre-existing before this follow-up, and out of scope for anything asked
here — flagged only so the log noise doesn't look alarming.
